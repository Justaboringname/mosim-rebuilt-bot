# mosim-rebuilt-bot：让 AI 打 MoSim REBUILT（4414 HighTide），一次没成功的研究

_Last updated: 2026-09-27_　·　[English](README.md) | **中文**　·　**[回放对比：人类 1118 vs bot](https://justaboringname.github.io/mosim-rebuilt-bot/replay/)**

目标：训练一个能自己开 4414 HighTide 打 [MoSimulator](https://store.steampowered.com/app/4398690/) REBUILT（FRC 2026）的 bot，超过人类个人最好成绩 **1118**，最好到 **1200**。结果没做到。这份文档讲清楚做了什么、每条路为什么走不通，以及学到的关于这个游戏和这类问题的东西。

项目由 Claude（Anthropic 的 AI）在用户指导下完成，全部实验在一台 Mac Studio（M5 Max）上跑。

## 结论先说

| | 分数 | 说明 |
|---|---|---|
| 人类最好成绩 | 1118 | 用户自己打的一局；另外两局录下的完整示范是 1085 和 1097 |
| **bot 最终** | **≈ 1021**（约 330 局） | 跟着人类示范路线开车的 tracker；单局最高 1084 |
| 目标 | 1200 | 没达到，项目停止 |

**为什么失败：不是“随机性太大、找不到梯度”。梯度量出来了：人类路线附近，测过的每个方向都是下坡或持平。**

1. **人类路线是一个很紧的局部最优。**
   - 我们在真游戏里量了十几种偏离或改进它的方式，结果全是亏或持平，例如 −34 ± 3、−18 ± 2.8、每局 −0.6 ± 0.5。早期几次只是单批或单局，误差大。
   - 已知的咬合点有两个：
     - 这条路线贴着球带边缘走，并保持约 10° 斜行。横移 0.6 m 就会错过球带；强行让车头对准行进方向，在 80–55 死窗口会亏 20。
     - 条带都是直的，因为车身一转，转塔就瞄不准，射门和传球都会停（见下文“转塔”）。
2. **随机性确实有影响，体现在两个具体地方：**
   - **球的分布会分叉。** 车碰到球几秒后，bot 的场面就和人类那局不一样了，照抄路线会“扫空气”。在 128 局对照里，bot 车上加存区的球在 105 s 平均比人类少约 32 个，在 55 s 少约 23 个。
   - **游戏不是确定性的。** 同一个存档读进两个实例、给完全相同的操作，第一步就差 8 mm（`-job-worker-count 0`；默认设置是 58 mm），15 秒后完全分叉。所以没法做 TAS（工具辅助速通）式的“试很多遍、挑最好那条再执行”。
3. **要跳出局部最优，就需要一条全新的好路线，而我们造不出来。**
   - 自建模拟器和静态估算器恰恰在关键处算错：
     - 对路线附近的小改动，模拟器连方向都算反：预测 +38 / +52，真游戏 −32 / −33。
     - 对大幅偏离，方向是对的，但损失被低估约 40%。
     - 覆盖估算器能正确判断会亏的方案，却把会亏 106 的方案判成了赚。
   - 在真游戏里盲搜又太慢：每小时只能跑几百局。设计评审估计，直接在真游戏里跑 PPO 要 10⁵ 次以上回放（这个数没有实测）。
   - 能提供新路线的只有人类示范，而现有几条示范几乎是同一条。
4. **1200 很可能超出这套打法的上限（估算）。**
   - 在 105–80 窗口，人类车上的球始终 ≥ 20 个，每秒约进 12.4 个球。
   - 整局约 1700 次送球：约 1118 次射门，加约 600 次传球。
   - 1118 已接近这类打法的天花板。要到 1200，得换一种运球思路，而不是把现有打法优化得更好。

## Harness：怎么接进游戏

- **挂载**
  - MoSim 启动时会构造 mod prefab 的 MonoBehaviour。`tools/Injector`（Mono.Cecil）在一个本地已安装的 mod DLL 的构造函数里插入一行调用，由它加载 `harness/MoSimRL`。我们用的是 China Modpack 的 `Alphabots.dll`；换成别的 mod，需要改 `install-hook.sh` 里的路径和类型名。
  - 没有 `run/ENABLE` 时，钩子只加载 DLL、写一行日志，不做别的。`tools/restore-hook.sh` 可以还原。
  - 安装脚本会把本仓库的 `run/` 路径写进 `~/.mosimrl_run`，让游戏内组件找到开关文件。bot 实例还会通过启动参数 `-mosimrl-run` 直接拿到这个路径。
- **控制**
  - `Bridge.cs` 在 `FixedUpdate` 里阻塞等待动作，每 22 个物理步（0.099 s 比赛时间）决策一次，通过 TCP JSON 和 Python 通信（`py/mosimrl/client.py`）。
  - 底盘调 `DriveController.overideInput`（场地坐标系），必须每个 FixedUpdate 都调，否则会退回读人类输入。
  - 5 个机构按键（Intake、AutoShoot、AutoPass、ManualShoot、RobotSpecial）通过 InputSystem 注入（`ButtonInjector.cs`），每次决策都重发完整的按键状态。
- **速度**
  - 无头模式（`-batchmode -nographics`），静音。
  - **固定帧步**：`Time.captureDeltaTime = 2 × fixedDeltaTime`，每帧严格推进 2 个物理步。游戏只受 CPU 速度限制，单实例约 4.3 倍实时；负载高低都不影响游戏逻辑。
  - 最终吞吐：20 个实例 + `-job-worker-count 0` + 精简状态，约每秒 348 个决策，比 16 个实例的默认配置快 27%。Python 每步只占 0.4 ms，不是瓶颈；瓶颈是游戏自己的物理计算。
- **存档 / 读档**
  - `Snapshot.cs` 用反射保存整场比赛：游戏 MonoBehaviour 字段、刚体、关节、管理器里按球索引的数组、静态字段和 `Random.state`，gzip + base64。
  - 存档能在另一个实例里读回，用来做真游戏前瞻（`py/mosimrl/planner.py`）。
  - 坑：锁住的关节读档后要重新锚定，否则吸球机构会失灵。
  - 读档只在统计意义上可信，在单个球的层面并不精确（见“混沌与确定性”）。
- **不上传排行榜**：只要 `run/BRIDGE`（或 `run/PROBE`）存在（gamectl 启动 bot 时会自动创建），harness 就在每个 Update / FixedUpdate / LateUpdate 把游戏的 `wasCheated` 置为 true，bot 的对局永远不会上传。只开 RECORD 录人类示范时不拦截，人类成绩照常上传。
- **自动化卫生**：实例带 `-mosimrl-owner <pid>` 启动，父进程退出后约 2 秒内自动退出，不会留下孤儿进程。

## 基线：跟着人类示范开（ghost tracker）

`py/mosimrl/ghost_policy.py`：按比赛时钟跟随人类那局的轨迹、车头朝向和按键，PD 位置控制加人类摇杆前馈。

| 版本 | 均分 | 关键改动 |
|---|---|---|
| 第一版脚本 | 148 / 139 | 卡在 bump 顶上、撞墙（这时用户录了示范局） |
| 跟车 + 开局修复 | 895 → 931 | 出 trench 横梁后再展开吸球 |
| CMA-ES 调 10 个跟车参数 | 1004 ± 23 | 提前量 0.15 → 0，位置增益 1.2 → 1.8 |
| 物理步时钟 | 1009 ± 22 | 游戏计时器按渲染帧走，机器一卡，决策会看到同一个 t |
| 固定帧步模式 | ≈ 998–1004 | 改成按 CPU 速度推进，属于换跑法，不是改进 |
| **车头时序 `yaw_dt = 0.2`** | **≈ 1022–1027** | 转弯时车头提前了 10–20°，把车头的时钟推后 0.2 s（相对固定帧步基线 +25，3.5 SE） |

后来有效的改动都来自**诊断执行误差**，不是来自搜索。

## 试过、被真游戏否决的方向

规则（从 MiniSim RL 候选 c50 起）：每个实验跑之前，在 `docs/research-log/proposals.md` 写好接受条件，真游戏里交替成对 A/B，增益 > 2 SE 才算数。更早的尝试（表中前五行、真游戏 MPC、连按 Intake）没有事先登记，MPC 和换路线的结果都是单局。

| 方向 | 想法 | 预测 | 真游戏结果 | 失败原因 |
|---|---|---|---|---|
| 贪心横向偏移 / RL 残差（早期） | 往球多的一侧偏 | — | 781 对 920 | 人类路线贴着球带边缘走，偏 0.6 m 就错过那条带（106 s 时车上 36 个对 80 个） |
| CMA 平移死窗口路线段 | 整段平移 | — | 约 800 对 1025 | 同上 |
| 路线拼接（1118 → 1097 → 1118） | 换一段别的示范 | — | 788 对 897（同批对照） | 要扫的区域已被另一条路线扫过 |
| 自由找球 | 哪里球多去哪 | — | 751 / 878 | 卡车，打乱扫球顺序 |
| 平滑弯曲路线（bump1） | 离线扫带模型选最优弯法 | 赚 | 869 对 1007 | 抢走下一趟要扫的球堆；卡车次数是 7 倍。把整个窗口放在一起算的联合模型符号对，但损失低估约 3 倍 |
| **MiniSim + PPO** | 按 PhysX 参数重写 3D 球物理，并按游戏行为重新实现比赛逻辑，在里面做 RL | 模拟 +38 / +52 | **−32 / −33** | 模拟器对“路线附近的小改动”连方向都算反，哪怕平均只偏 5 cm |
| 真游戏 MPC（存档前瞻） | 每 2 s 从存档推演候选，选最好的 | — | 单局：死窗口 MPC 987（基线约 998），主动窗口 MPC 892 | 12 s 推演视界太短，损失落在视界之外 |
| 在人类路线之间切换 | 3 条人类路线加镜像共 6 条，按推演选 | — | 单局 m3：所有换路线候选的推演都比跟车差 27–71，实际 0 次切换（1031） | 几条示范几乎相同 |
| 射门时连按 Intake | 用户的建议 | — | −26 到 −43 | 人类只在窗口末尾这么做，跟车已经照搬了 |
| 吸球时车头对准前进方向（IF） | 让球从吸口正中进 | — | 80–55 死窗口 −20 | 人类约 10° 的斜行是有意的 |
| 看着球走（LBS） | 每 0.1 s 选局部吸得最多的走法 | 局部赚 | 130→105 持球 −34（整局 881 对 1014，纯横移变体） | 覆盖出现空隙：130→105 结束时中场多剩约 50 个球，80→55 多剩约 25 个 |
| 球堆配准（REG） | 把人类每段路线平移到那堆球现在的位置 | — | 130→105 持球 −24 | 同上 |
| **整窗口覆盖重规划（CR）** | 静态场估算器 + 束搜索，按实际的球重排整个窗口 | 估算 +25 | **130→105 持球 −106**（选择性版本 −89；整局 886 对 1016） | 规划路线一直在转：转塔瞄不准，车里满到 90–100 个，后面吸不进来 |
| 射门时限制转速（ys60） | 转塔在车身不转时射得快 | 筛选 +6.9 | **−18.3**（1003.9 对 1022.2，各 128 局） | 筛选评分把窗口结束时的持球按 1 分算，是个漏洞；真实进球变少，原因没有定位 |
| **真游戏选项学习 RL（OL）** | 随机化“转弯射门时限速”和“55 秒前憋球”，从约 4000 次真游戏回放学条件策略 | — | 交叉验证 **每局 −0.6 ± 0.5**（门槛 +5） | 模型能预测限速在哪里亏得多，却找不到能赚的情况；憋球的效果是 0 |

- LBS / REG / CR 只量了第一个死窗口（130→105），单位是窗口结束时的持球数（车内 + 存区），不是分。
- 另外确认了游戏**不是确定性的**，所以 TAS 式搜索做不了（这是检查，不是 A/B）。
- 有两处记录在案的例外：CR 在止损后，应用户要求仍进了真游戏；OL 第一次检查里的朝向恢复率门槛要求 ≥ 0.90，实测 0.80，仍然放行。

## 关于游戏的发现

**计分**
- 每个球 1 分，按“穿过”判定，每球 1.5 s 防抖。4414 没有爬升机构，全部得分来自 fuel。
- hub 关闭后 **3 s 内**进的球仍然算分。人类会在关闭后继续射约 1.3 s，在 1118 那局里每次多拿 44–46 分。
- `run_ghost` 的逐窗口统计漏掉了终场哨后还在飞的球（平均约 24 分，5–95% 区间 8–35）。比较逐窗口得分时要把它们加回去。

**吸球（4414）**

滑轨完全伸出（≥ 0.29 m）时，按球偏离车中线的距离，吸入概率是：

| 横向偏移 | 吸入概率 |
|---|---|
| ≤ 0.30 m | 0.95–0.98 |
| 0.30–0.35 m | ≈ 0.80 |
| 0.35–0.40 m | ≈ 0.6 |
| 0.40–0.45 m | 0.35–0.48 |
| 更外侧（到 0.555 m） | ≈ 0.15，大多被前角推开 |

- 首次接触发生在前角的球，整体只有 0.38 被吸进。车速没有可测的影响。
- 按住 AutoShoot / AutoPass 却不按 Intake 时，滑轨缩到约 0.19–0.25 m，碰到的球约 70% 被推开。
- 车里 ≥ 81 个球时吸入率降到 0.80，≥ 96 个时降到 0.56。
- 对照组 130→105 窗口里，约 38 个球被车碰过但没吸进，约 16 个被连带推开（80→55：45 / 12）。

**转塔与车身转动（最重要的一条）**

对照组，按住 AutoShoot、车里 ≥ 20 个、在本方区域内：

| 车身转速 | 占射门时间 | 每秒发射 | 转塔误差 |
|---|---|---|---|
| < 20°/s | 55% | 16.7 | 0.22 |
| 20–60°/s | 26% | 16.1 | — |
| 60–120°/s | 14% | 13.7 | 0.51 |
| > 120°/s | 4% | 4.0 | 1.27 |

- 车身一转，转塔误差变大，送球门控会挡住发射。传球（AutoPass）也一样：直走时每秒约 20 个，转速超过 120°/s 时只剩 2–6 个。
- 这就是 CR 大亏的原因：规划的路线一直在转，车里的球停在 90–100 个，中场被清走的球少了约 110 个。
- 这组数是相关关系，不过转塔误差随转速上升，正是门控挡住发射的直接条件。
- 反过来，强行限制转速**也亏**（ys60、OL），原因没有定位：ys60 下窗口结束时持球反而更多，进球却更少。

**持球的价值（窗口评分必须校准）**

窗口结束时车里或存区的一个球，折算成后续得分：

| 时间点 | 一个持球约值 |
|---|---|
| 105 s | 0.6–0.8 分 |
| 80 s | ≈ 0.35 分（0.24–0.43） |
| 55 s | ≈ 0.55 分（车内约 0.7，存区约 0.4） |
| 30 s | ≈ 0 分 |

按 1 分算会被优化器钻空子，ys60 的筛选就是这样通过的。

**混沌与确定性**
- 同一策略下的两局 bot，首次扫球 10 s 后，只有约 38% 的地面球位置能对上（误差 5 cm 以内）。
- 同一存档读进两个实例、操作完全相同，第一步机器人就差 8 mm，15 s 后两边的球最多相差 11 m。同一实例重读一次也一样。
- 同一存档推演 22 s，持球数（车内 + 存区，均值约 371）的标准差约 6.6，只看车内约 8.3。独立整局得分的标准差约 23。

**人类 1118 对 bot 1084（bot 最高的一局）**

| 阶段 | 人类 | bot | 差 |
|---|---|---|---|
| 自动 + 140–130 | 207 | 214 | +7 |
| 130 s hub 关后宽限 | 46 | 38 | −8 |
| 105–80 主动 | 286 | 272 | −14 |
| 80 s hub 关后宽限 | 44 | 34 | −10 |
| 55–30 主动 | 278 | 269 | −9 |
| 30–0 | 233 | 225 | −8 |
| 终场哨后 | 24 | 32 | +8 |

- 130 s 时人类车上还有 39 个球，bot 只有 17 个，所以宽限期少射了。
- 死窗口里，人类用同一条路线清掉中场 85% / 81% 的球；bot 这局是 82% / 75%，对照组（8 局均值）是 75% / 75%。
- 可以在 [回放对比页](https://justaboringname.github.io/mosim-rebuilt-bot/replay/) 里并排看这两局，页面上有跳到这些时刻的按钮。

## 方法上的教训

1. **模拟器会把小改动的方向算反。** MiniSim 对原路线的总分只差约 20 分，但对“偏 5 cm”这类残差给出的方向是错的。用模拟器训练残差策略前，先在真游戏里验证它能不能给这类改动排对顺序。
2. **估算器必须在“它说会赚”的案例上回测**，不能只在“它说会亏”的案例上回测。CR 的估算器能正确判断 LBS 会亏，却把会亏 106 的方案判成了赚。
3. **筛选评分会被钻空子。** 窗口结束时的持球按 1 分算，就会奖励“少射多囤”。价值要按后续实际得分回归校准，最终只认整局得分。
4. **配对方式会制造假信号。** 按回放完成的先后配对，会系统性地挑出跑得快（球少、分低）的回放。要按提交顺序配对。
5. **事先写好接受和止损条件。** 从 c50 起，每个方向都按这个规则止损，没有事后改门槛（两处例外见上）。
6. **CPU 占满不等于满负荷。** 采样器派活不够时，一半实例在空等，系统看起来却还是“CPU 100%”。要看每秒决策数，不要看占用率。

## 如果有人想接着做

- 最可能有用的：**录几局死窗口路线明显不同的人类示范**。这是唯一还没真正试过的杠杆，现有示范几乎是同一条路线。
- 在真游戏里做**能改路线的深度 RL**：需要几天算力，先验成功率低。
- 别再试的，都已经量过：
  - 局部偏离人类路线：横移、平移、弯曲、找球、配准；
  - 不改路线的执行层小杠杆：限速、憋球、连按。

| `py/minisim/` | MiniSim：PhysX 参数的球物理加比赛逻辑的重新实现、PPO（`rl.py`）和校准脚本 |

- **包含的游戏数据**：`py/minisim/field_obbs.json`、`robot_obstacles.json` 是从游戏场地场景读出来的碰撞体尺寸（只有数字，回放页的场地轮廓也来自这里）。`hit_table.json`、`launch_table.json` 是我们自己的测量。
- **不包含**：游戏或其他 mod 的代码、反编译结果、二进制和美术素材，以及约 16 GB 的实验数据。代码注释和实验记录里提到的 `runs/`、`docs/design/`、`docs/policy-facts/` 是没有公开的工作文件。

## 运行

需要：
- macOS；
- Steam 版 MoSimulator 26.4.1（REBUILT 只在 Steam 版里有）；
- 一个本地安装的 mod（用来挂钩）；
- .NET SDK（编译 harness 和 injector）；
- Python 3.11，依赖见 `requirements.txt`。

```bash
dotnet build harness/MoSimRL -c Release   # 生成 harness/bin/MoSimRL.dll
tools/install-hook.sh                      # 先退出游戏；用 tools/restore-hook.sh 还原
touch run/ENABLE
cd py && python -m mosimrl.run_ghost --demo ../run/demos/demo-20260926-015440-m1.jsonl --ports 47500,47501 \
    --episodes 4 --time-scale 1 --steps-per-frame 2 --game-args "-job-worker-count 0"
python -m mosimrl.replay ../runs/ghost/<batch>/<match>.json --out /tmp/data.js   # 生成回放数据
```

- 录人类示范：`touch run/ENABLE run/RECORD`，再从 Steam 正常开游戏打一局，录像写到 `run/demos/`。
- bot 对局一律无头、静音、不上传成绩。
- 公开前改过游戏内组件查找 `run/` 目录的方式（原来写死在作者自己的路径上），新方式只做了编译检查，没有在游戏里重新跑过。
